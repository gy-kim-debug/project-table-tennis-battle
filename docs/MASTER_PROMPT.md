## 0. 프로젝트 목표 및 역할

너는 Godot 4 기반 iOS 모바일 게임 개발을 담당하는 시니어 게임 개발자이자 테크니컬 리드다.

이 프로젝트의 목표는 **세로형 모바일 화면에서 플레이하는 2D 도트 그래픽 기반 원버튼 타이밍 탁구 배틀 게임을 제작하여 Apple App Store에 출시하는 것**이다.

사용자는 프론트엔드 개발 경험이 있으며 Godot를 활용한 게임 개발은 처음이다.

개발 과정은 다음과 같이 역할을 분리한다.

**Codex 담당**
- 게임 기획 구체화 및 기술 설계
- Godot 프로젝트 생성 및 환경 설정
- GDScript 코드 작성
- 게임 씬 및 노드 구성
- 전투 및 타이밍 시스템 구현
- 상대 AI 구현
- 공 패턴 및 궤적 구현
- UI와 애니메이션 연결
- 그래픽 에셋 통합
- 자동 테스트 및 버그 수정
- 성능 최적화
- iOS 빌드 및 배포 준비
- 프로젝트 문서 작성 및 유지

**ChatGPT 담당**
- 실제 게임에 사용할 2D 도트 그래픽 에셋 제작
- 플레이어와 상대 캐릭터 이미지
- 탁구대, 배경, 공 이미지
- 캐릭터 애니메이션 스프라이트
- UI 도트 그래픽 및 이펙트 이미지
- 필요시 App Store용 이미지 제작

**사용자 담당**
- 게임 기획과 중요한 설계 결정
- 실제 플레이 및 타격감 검수
- ChatGPT 생성 에셋 제공
- iPhone 실기기 확인
- Apple 개발자 계정 관련 승인
- 최종 출시 결정

Codex는 실제 에셋이 준비되기 전까지 임시 도형과 플레이스홀더로 게임을 구현한다.

### 최우선 개발 원칙

1. 실제로 실행 가능한 게임을 먼저 만든다.
2. 게임 로직과 그래픽을 분리한다.
3. 코드는 단순하고 유지보수 가능하도록 설계한다.
4. 과도한 추상화와 불필요한 시스템은 만들지 않는다.
5. 현재 작업 범위를 벗어난 기능을 임의로 추가하지 않는다.
6. 핵심 게임 규칙은 사용자의 승인 없이 변경하지 않는다.
7. 기능을 단계별로 구현하고 검증한다.
8. 중요한 설계와 결정은 프로젝트 문서에 기록한다.
9. 게임의 재미와 모바일 조작성을 기술적 화려함보다 우선한다.
10. 구현하지 않은 기능이나 검증하지 못한 동작을 완료했다고 보고하지 않는다.

# 1. 기술 스택 및 플랫폼

## 1.1 개발 환경

- 엔진: Godot 4.x 안정 버전
- 언어: GDScript
- 게임 유형: 싱글플레이 2D
- 최초 출시 플랫폼: **iOS**
- 우선 지원 기기: iPhone
- 배포 플랫폼: Apple App Store
- 화면 방향: 세로 고정
- 기준 화면 비율: 9:16
- 그래픽 스타일: 전체 2D 도트 그래픽
- 이미지 형식: PNG
- 기본 텍스처 필터링: Nearest
- 버전 관리: Git

실제 개발에 사용할 Godot 안정 버전은 프로젝트 생성 시 확인하고 문서에 기록한다.

내부 기준 해상도는 우선 360×640을 검토한다.

단, 최종 해상도는 픽셀아트의 일관성, 공의 가독성, iPhone 화면에서의 표시 품질을 기준으로 결정한다.

## 1.2 플랫폼 원칙

**Android는 초기 개발 및 출시 대상에서 제외한다.**

사용자는 Android 기기를 소유하고 있지 않다.

따라서 Android 빌드, Google Play, Android SDK 설정은 MVP 범위에 포함하지 않는다.

다만 향후 Android로 확장할 가능성을 고려하여 게임 로직에 불필요한 iOS 전용 의존성을 만들지 않는다.

## 1.3 iOS 개발 준비

초기에 다음 환경을 확인한다.

- macOS 사용 여부
- Xcode 설치 및 버전
- Godot iOS Export Template
- Apple Developer Program 가입 여부
- iPhone 실기기 연결 및 테스트 가능 여부
- Apple 코드 서명 및 프로비저닝 준비 상태

확인할 수 없는 사항을 임의로 충족되었다고 가정하지 않는다.

계정 로그인, 인증서 생성, 실제 앱 제출 등 사용자 권한이 필요한 작업은 실행 전에 필요한 사용자 조치를 명확하게 요청한다.

# 2. 게임 핵심 콘셉트

## 2.1 게임 장르

**타이밍 액션 + 체력 기반 탁구 배틀**

이 게임은 정교한 탁구 물리 시뮬레이터가 아니다.

탁구의 랠리 구조에 타이밍 액션과 체력 기반 전투를 결합한 모바일 아케이드 게임이다.

## 2.2 핵심 플레이

1. 상대 AI가 탁구공을 보낸다.
2. 공이 플레이어 방향으로 날아온다.
3. 플레이어는 정확한 순간에 화면을 터치한다.
4. 타격 타이밍에 따라 Perfect / Good / Bad / Miss 판정이 발생한다.
5. 타격에 성공하면 상대에게 공을 되돌린다.
6. 상대 AI가 플레이어의 공격에 대해 수비 판정을 수행한다.
7. 상대가 공을 받아내면 랠리가 이어진다.
8. 상대가 공을 놓치면 상대 HP가 감소한다.
9. 플레이어가 공을 놓치면 플레이어 HP가 감소한다.
10. 먼저 HP가 0이 되는 쪽이 패배한다.

한 경기의 목표 플레이 시간은 약 1~3분이다.

# 3. 게임 시점 및 화면 구성

## 3.1 카메라

**플레이어 캐릭터 후방 대각선 20도 고정 시점**

이 카메라 구도는 프로젝트의 확정 사양이다.

- 카메라 좌우 이동 없음
- 카메라 회전 없음
- 카메라 자동 추적 없음
- 카메라 각도 변화 없음
- 플레이어 캐릭터 이동 없음
- 별도의 3D 카메라 없음

Godot 2D 기능을 사용한다.

탁구대와 공의 위치, 크기 변화를 통해 원근감을 표현한다.

실제 3D 모델을 생성하지 않는다.

카메라를 이동시켜 역동성을 표현하는 대신 공, 캐릭터, 타격 애니메이션, 사운드, 도트 이펙트로 액션성을 만든다.

## 3.2 화면 레이아웃

세로형 9:16 기준:

**상단**
- 상대 HP
- 상대 캐릭터
- 필요시 상대 상태 표시

**중앙**
- 탁구대
- 네트
- 공
- 공의 바운드 및 이동 궤적

**하단**
- 플레이어 캐릭터
- 플레이어 HP
- 타격 판정 피드백

모든 중요한 게임 요소는 iPhone의 Safe Area를 고려하여 배치한다.

공은 작은 화면에서도 명확하게 구분되어야 한다.

# 4. 조작 시스템

조작은 반드시 하나로 유지한다.

**화면 터치 한 번 = 라켓 스윙**

개발 및 디버깅 편의를 위해 마우스 클릭과 키보드 입력도 지원할 수 있다.

하지만 최종 게임의 핵심 조작은 화면 터치 하나다.

다음 입력 방식은 사용하지 않는다.

- 이동 방향키
- 가상 조이스틱
- 좌우 드래그
- 별도의 공격 버튼
- 별도의 방어 버튼
- 별도의 스매시 버튼

플레이어의 좌우 이동은 구현하지 않는다.

공의 좌우 코스는 시각적인 패턴으로 사용하며, 모든 공은 고정된 플레이어가 타이밍 입력만으로 받아칠 수 있어야 한다.

## 4.1 입력 제한

- 하나의 공에 대해 하나의 스윙만 허용
- 스윙 중 추가 입력 무시
- 연타로 타이밍 판정을 우회할 수 없도록 처리
- 타격 가능 구간 밖의 입력도 적절한 실패 처리
- 전투 종료 및 결과 화면에서는 전투 입력 차단

# 5. 타이밍 판정 시스템

공의 타격 기준 시점과 플레이어 입력 시점의 차이를 기준으로 판정한다.

초기 수치는 다음과 같다.

| 판정 | 타격 오차 |
|---|---|
| Perfect | ±50ms |
| Good | ±120ms |
| Bad | ±180ms |
| Miss | 그 외 |

상위 판정 범위를 먼저 계산한다.

예를 들어 오차가 40ms라면 Perfect이며 Good 판정과 중복되지 않는다.

입력을 하지 않은 상태로 공이 타격 가능 구간을 지나면 자동으로 Miss 처리한다.

너무 이르게 스윙한 경우에도 해당 공에 대해 새로운 스윙을 할 수 없어야 한다.

타이밍 판정은 렌더링 프레임 및 스프라이트 애니메이션에 종속되지 않는다.

판정 시간은 게임 내부의 일관된 시간 기준으로 계산한다.

iPhone의 실제 터치 반응 지연을 테스트하고 필요하면 판정 보정값을 제공할 수 있도록 설계한다.

모든 판정 수치는 코드 여러 곳에 하드코딩하지 말고 조정 가능한 데이터로 관리한다.

# 6. 체력 기반 전투

## 6.1 시작 체력

- 플레이어 HP: 100
- 상대 HP: 100

## 6.2 피해 발생 조건

**공격을 성공적으로 쳤다는 이유만으로 HP가 감소하지 않는다.**

상대가 공을 받아내지 못했을 때만 상대 HP를 감소시킨다.

플레이어가 공을 놓쳤을 때는 플레이어 HP가 감소한다.

공을 정상적으로 주고받는 동안에는 피해가 발생하지 않는다.

## 6.3 초기 피해량

| 상황 | 피해량 |
|---|---:|
| 일반 공 Miss | 12 |
| Perfect 공격 Miss | 18 |
| 플레이어가 일반 공 Miss | 12 |
| 플레이어가 강한 공 Miss | 18 |

피해량은 초기 밸런싱을 위한 가정값이다.

한 번의 Miss 이벤트에 피해가 중복 적용되지 않아야 한다.

HP는 0~최대 HP 범위를 벗어나지 않는다.

## 6.4 랠리 규칙

- 성공적인 리턴 → 랠리 지속
- 어느 한쪽 Miss → HP 감소
- Miss 이후 → 현재 랠리 종료
- HP가 남아 있다면 → 다음 랠리 시작
- HP가 0이라면 → 전투 종료

랠리 시작 주체 및 서브 순서는 초기에는 단순하게 구성하되, 일관된 규칙으로 구현한다.

# 7. 타격 성능

타이밍 판정 결과는 공격 위력에 영향을 준다.

| 판정 | 공격 성능 |
|---|---:|
| Perfect | 100 |
| Good | 65 |
| Bad | 30 |
| Miss | 0 |

공격 성능은 직접 HP 피해량이 아니다.

상대 AI에게 전달되는 수비 부담을 나타낸다.

### Perfect
- 강한 공격
- 상대의 수비 부담 증가
- 압박 증가
- 강렬한 이펙트와 사운드

### Good
- 안정적인 공격
- 일반적인 리턴
- 적당한 압박 증가

### Bad
- 약한 공격
- 상대가 반격하기 쉬운 상황
- 낮은 공격 성능

### Miss
- 공격 실패
- HP 감소
- 랠리 종료

# 8. 상대 AI 시스템

MVP에서는 상대 AI 캐릭터 한 명을 구현한다.

상대 AI는 복잡한 머신러닝이 아니라 **규칙 및 패턴 기반 시스템**으로 개발한다.

## 8.1 AI 역할

- 공격 패턴 선택
- 공 발사
- 플레이어 공격에 대한 수비 판정
- 수비 성공 시 반격
- 압박 수치 반영
- 난이도에 따른 행동 차이

## 8.2 AI 수비 판정

AI는 다음 결과 중 하나를 가진다.

- Perfect
- Good
- Bad
- Miss

Perfect, Good, Bad인 경우 공을 받아내고 랠리가 이어진다.

Miss인 경우 피해를 받고 랠리가 종료된다.

상대의 수비 결과는 플레이어 공격 성능, 압박 수치, 패턴 난이도, AI 방어 능력을 고려하여 계산한다.

무작위 요소를 사용할 경우 테스트 재현을 위해 고정 시드를 지원한다.

실제 수비 계산식과 임계값은 Codex가 초기 제안을 작성하고, 밸런싱 가능한 데이터로 관리한다.

# 9. 압박 시스템

상대 AI는 0~100의 압박 수치를 가진다.

초기 규칙:

| 이벤트 | 압박 변화 |
|---|---:|
| 플레이어 Perfect | +35 |
| 플레이어 Good | +15 |
| 플레이어 Bad | -15 |
| 플레이어 Miss | 초기화 |
| 상대 Perfect 수비 | -25 |
| 상대 Good 수비 | -10 |

압박 수치는 0~100 범위로 제한한다.

압박이 높을수록 강력한 공격을 방어하기 어려워진다.

압박만으로 결과가 무조건 결정되는 단순한 구조는 피한다.

초기 버전에서는 압박 게이지를 사용자에게 반드시 표시할 필요는 없다.

다만 내부 상태 확인을 위한 개발용 디버그 정보는 제공할 수 있다.

# 10. 공 이동 및 패턴 시스템

실제 탁구 물리 엔진 대신 **이벤트·패턴 기반의 공 이동 시스템**을 구현한다.

공은 시간에 따라 사전 정의된 궤적으로 움직인다.

시각적으로는 자연스러운 포물선과 탁구대 바운드가 표현되어야 한다.

## 10.1 공 패턴 데이터

각 패턴은 다음 속성을 가질 수 있다.

- Pattern ID
- 이동 시간
- 타격 기준 시간
- 시작 위치
- 목표 위치
- 좌우 이동 궤적
- 높이 궤적
- 바운드 시점
- 속도 특성
- 공격 강도
- 패턴 난이도

데이터를 별도로 관리하여 공 패턴을 추가하기 쉽게 구성한다.

## 10.2 MVP 패턴 5종

### Pattern 01 — 기본 리턴
- 중앙 방향
- 일정한 속도
- 예측하기 쉬운 타이밍

### Pattern 02 — 빠른 스매시
- 빠른 이동
- 낮은 궤적
- 짧은 반응 시간

### Pattern 03 — 높은 로브
- 높은 궤적
- 느린 이동
- 기다리는 타이밍이 중요

### Pattern 04 — 낮은 드라이브
- 낮은 바운드
- 빠른 접근
- 어려운 타이밍

### Pattern 05 — 템포 체인지
- 느린 도착
- 평소와 다른 리듬
- 성급한 입력을 유도

모든 공 패턴은 원버튼만으로 받아칠 수 있어야 한다.

실제로 도달할 수 없는 위치에 공을 보내는 방식으로 난이도를 높이지 않는다.

## 10.3 2D 원근 표현

공의 깊이감은 다음 요소로 표현한다.

- 화면 좌표 변화
- 공 크기 변화
- 공 높이 변화
- 그림자 위치
- 바운드 애니메이션
- 잔상
- 타격 이후 궤적 전환

공의 논리적 궤적과 시각적 표현은 분리한다.

스매시 전용 복잡한 게이지나 필살기 버튼을 만들지 않는다.

## 11.4 전투 종료

# 15. 그래픽 에셋 제작 및 통합

모든 최종 비주얼은 2D 도트 그래픽을 사용한다.

Codex가 직접 최종 아트를 제작하는 것은 기본 작업 범위에서 제외한다.

초기에는 Godot의 기본 도형과 플레이스홀더로 게임을 구현한다.

ChatGPT에서 제작한 그래픽을 제공받으면 해당 파일을 Godot 프로젝트에 통합한다.

## 15.1 기본 원칙

- 에셋 크기와 비율 일관성
- 캐릭터 방향 일관성
- 애니메이션 프레임 정렬
- 픽셀 깨짐 방지
- Nearest 필터링
- 모바일 화면에서 충분한 명도 대비
- 공과 배경의 시각적 구분
- 교체 가능한 에셋 구조

## 15.2 캐릭터 방향

플레이어는 후방 대각선 20도에서 보이는 모습으로 제작한다.

상대는 플레이어를 마주 보는 방향으로 제작한다.

카메라는 고정되므로 여러 카메라 각도에 대응하는 대량의 캐릭터 스프라이트를 만들 필요는 없다.

최초에는 다음 애니메이션을 우선한다.

- Idle
- Swing
- Perfect Swing
- Miss
- Hit
- Victory
- Defeat

초기 MVP에 필요하지 않은 애니메이션은 이후 단계로 미룰 수 있다.

## 15.3 에셋 요청 절차

그래픽이 필요한 단계에서 Codex는 ASSET_SPEC.md를 기준으로 필요한 에셋 목록을 제시한다.

ChatGPT에서 제작할 수 있도록 구체적인 이미지 생성 요구사항을 작성한다.

사용자가 에셋을 제공하면 다음을 수행한다.

1. 이미지 규격 확인
2. 투명 배경 및 프레임 구성 확인
3. Godot Import 설정
4. 스프라이트 및 애니메이션 연결
5. 실제 게임 화면에서 표시 확인
6. 문제가 있으면 필요한 수정 사항 기록

# 20. 프로젝트 작업 방식

모든 개발 작업은 다음 절차를 따른다.

1. 프로젝트 파일 및 현재 상태 확인
2. AGENTS.md 확인
3. 관련 GAME_DESIGN.md 확인
4. 해당 작업의 목표와 범위 확인
5. 필요한 파일만 수정
6. 가능한 자동 테스트 실행
7. 실행 결과 확인
8. 관련 프로젝트 문서 업데이트
9. 변경 사항과 남은 문제 보고

작업 중 중요한 설계 변경이 필요하면 이유, 대안, 영향 범위를 설명한다.

게임 기획을 변경해야 하는 경우 사용자의 결정을 받는다.

작은 구현 세부 사항은 이미 확정된 설계 범위 안에서 합리적으로 결정할 수 있다.

현재 단계가 끝나지 않은 상태에서 이후 Phase 기능을 대규모로 구현하지 않는다.

### 이번 작업

### 알려진 문제
현재 발견된 문제 및 기술적 위험

### 다음 작업
다음 단계에서 가장 우선해야 할 작업

검증하지 않은 기능을 정상 작동한다고 단정하지 않는다.

# 22. 최초 실행 지시

이 마스터 프롬프트를 프로젝트의 공식 기준으로 사용한다.

**첫 작업에서는 Phase 0만 수행한다.**

다음 순서로 진행한다.

1. 현재 작업 디렉터리 및 프로젝트 상태 확인
2. Godot 개발 환경 확인
3. iOS 개발 환경에서 확인 가능한 사항 점검
4. 프로젝트 디렉터리 구조 설계
5. 프로젝트 루트에 AGENTS.md 생성
6. docs/GAME_DESIGN.md 생성
7. docs/ARCHITECTURE.md 생성
8. docs/ASSET_SPEC.md 생성
9. docs/ROADMAP.md 생성
10. 모든 문서의 규칙 및 용어 일관성 검토
11. Git 상태 확인 및 필요한 초기 설정
12. Phase 1 구현 작업의 세부 계획 작성

이미 존재하는 파일은 내용을 확인하고 불필요하게 덮어쓰지 않는다.

게임 기획에 확정되지 않은 사항이 있다면 해당 문서에 미결정 사항으로 기록한다.

문서에 기록한 수치와 규칙 중 초기 가정인 항목을 명확히 구분한다.

**이번 작업에서는 Godot 전투 시스템 코드를 구현하지 않는다.**

Phase 0 완료 후 생성한 파일과 주요 설계 내용을 보고하고, Phase 1 구현을 시작하기 위한 다음 작업을 제안한다.

최종 목표는 유지보수 가능한 구조와 일관된 도트 그래픽을 갖춘, 실제 iPhone에서 플레이할 수 있는 원버튼 체력 기반 탁구 배틀 게임을 완성하는 것이다.
